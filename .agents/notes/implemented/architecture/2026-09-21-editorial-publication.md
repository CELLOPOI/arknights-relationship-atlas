# 日常资料在后台审核发布，Git 保存代码与资料快照

Status: implemented
Date: 2026-09-21

用户在重新评估资料 PR 的维护成本后，要求完成后台更新并提交 Git。原流程需要编辑导出单条候选，由开发者整理 PR、合并和运行发布命令；新增人物及关联关系不能一起在后台完成。项目已经具备 Django、PostgreSQL、稳定资料 schema 和受控发布，无需另换框架。

新增资料修订，包含多条候选、修改说明、审核状态和事件历史。数据库中的已发布版本为正式依据；第一次后台发布后关闭旧 Git 包写入。Git 保留代码、初始化基线和单向导出的版本快照，不引入双向合并。候选与修订保持私有，发布快照只含正式资料白名单。

修订需要完成编辑、整体校验、审核、带版本预览和事务发布。保留发布状态锁、数据库漂移检查、方向及证据约束、素材校验、公开读取一致性、显式撤下和新版本回退。锁顺序为发布状态、修订、条目、反馈。审核通过后冻结内容；退回修改必须重新审核。发布预览绑定内容、操作者、基线和关联反馈版本，反馈结案与资料发布共用事务。小团队允许兼任，操作记录不冒充独立审核。

真实备选包括：保留手工资料 PR，优点是复用公开审查但编辑操作仍繁琐；后台自动创建 PR，能隐藏部分 Git 操作，但日常发布仍依赖 GitHub 凭据、合并和交付；后台正式发布能完成网页维护闭环，代价是本系统需要承担权限、审核、并发、审计及恢复。当前选择复用已有模型和发布约束，避免分别维护数据库与 Git 两份可独立写入的权威数据。

替代 [2026-09-20 Git 权威发布决定](2026-09-20-git-authoritative-release.md) 中关于日常正式资料来源和候选导出的部分；该记录的来源核对、证据身份、条件叙事、事务一致性与灾难恢复边界继续有效。旧独立候选可原样纳入新修订；既有数据库先执行增量迁移，首个基线仍须核对，不能清库重导。

当前后台编辑覆盖五类正式记录。条件叙事及来源贡献保留并随快照和回退处理，暂未提供专门编辑器；后续上游批次可增加带差异的修订导入，但不能把导出快照当作另一条自由写入口。当前验证和部署边界集中在 [后台更新验收](../../../../docs/EDITORIAL_VALIDATION.md)；操作说明见 [后台维护](../../../../docs/EDITORIAL_WORKFLOW.md)。
